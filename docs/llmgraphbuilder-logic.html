02 / system architecture

システムはどうつながるか

取り込み時に作るグラフを、質問時に検索する。LLMは「抽出」「質問の書き換え」「回答生成」で使われ、埋め込みモデルとリランカーは別の役割を持つ。

図は横にスクロールできます。

3種類の「Document」を区別する

Neo4jのDocumentノードは登録ファイル。LangChainのDocumentは本文＋メタデータの入れ物。回答用の文書ブロックは検索で選んだチャンクを元文書単位に束ねたもの。8件の上限が掛かるのは最後のブロック。

2種類のグラフ関係

PART_OF・HAS_ENTITYは根拠への接続。Entity → Entityは意味的な関係。REFERS_TOは文章中の「別表参照」などを表し、検索で追加本文を取りに行くために使う。

根拠：score.py、main.py、rerank_retriever.py

03 / complete retrieval pipeline

質問から回答まで、順番に追う

現在の標準経路 graph_vector_fulltext ＋ CHAT_RERANK_ENABLED=true。件数は取得数の保証ではなく上限。該当データ・点数・参照関係の有無で減る。

質問・履歴・検索設定を受け取る

画面から /chat_bot へ質問、モデル、モード、文書選択、検索の変更値を送る。履歴を含めたメッセージが1件なら原文の質問を使い、複数件ならLLMで検索用の質問に書き換える。

以降の埋め込み・リランク・エンティティ類似度には、この検索用質問を使う。回答生成には元の質問と会話履歴を渡す。

ベクトル検索と全文検索を統合し、最大20候補

ベクトル索引に 20 × 5 = 100件を要求し、その枝を20件までにする。全文索引は最大20件。各枝で点数を最大点により正規化し、同じノードは高い方の点数を採用して、統合後に上位20件へ切る。

切り捨て①：各枝のtop-k、および統合後top-k。詳細は ハイブリッド検索図。

候補点数が0.5未満なら除外

candidate_min_score=0.5。20件を得た後にフィルタする。例えば7件が閾値未満なら残り13件になり、落ちた7件の補充検索はしない。

切り捨て②：候補検索の点数 < 0.5。リランカーの点数ではない。

本文をリランクし、最大6チャンクを選ぶ

各候補本文と質問の組をクロスエンコーダで採点する。各本文は先頭3,000文字だけを採点に使い、点数順の上位6件を残す。チャンク採用用のリランク最低点は別途設けていない。

切り捨て③：順位7位以下。採点に使わない部分：3,001文字目以降。採用後の本文はこの文字数では切られない。

参照先本文を最大2チャンク追加

現在は reference_select=target。6件の選択チャンクから REFERS_TO を1回たどり、未選択の参照先Chunkを最大100行取得。参照先本文を質問でリランクし、上位2件を追加する。

切り捨て④：参照先の取得上限100、そこから上位2件。参照先がなければ追加0件。標準設定では直接6＋参照2＝最大8チャンク相当。

文書単位で束ね、起点エンティティを40件へ

直接選択＋参照追加チャンクを所属Documentごとにまとめる。その中の HAS_ENTITY 接続先を候補にし、質問との埋め込み類似度順、同点なら選択チャンク内での出現数順に並べる。各文書の上位40起点を残す。

切り捨て⑤：選択チャンクに接続していないエンティティは起点にならない。各文書の起点候補41位以下も落ちる。

起点の類似度で0・1・2ホップを決める

0.3未満は起点自身だけ。0.3〜0.9または埋め込みなしなら0〜1ホップ。0.9超なら0〜2ホップ。現在、1ホップ経路数は無制限、2ホップは起点ごと最大40経路。取得後にノード・関係の重複を除く。

切り捨て⑥：ホップ範囲、除外関係・終点ラベル、2ホップの経路上限。展開先の全ノードを類似度で再フィルタする処理はない。

本文を確保し、グラフ行を採点して詰める

文書を「含まれる選択チャンクの最大リランク点数」で並べる。本文はすべて残す。エンティティ行・関係行を全文書から集め、同一文字列を重複除去し、質問でリランク。点数順に最大120行、本文との合計が14,000文字予算に収まる範囲で加える。

切り捨て⑦：行の点数下限、120行、次の行が文字予算に入らない時点で全体終了。本文だけで予算を超えても本文は残る。

最大8文書ブロックにし、回答を生成

format_documents() でもう一度文書スコア順に並べ、最大8ブロックへ切る。出典付きの Document start … Document end 形式でLLMへ渡す。現在のローカルLLM設定では出力は最大4,096トークン。

切り捨て⑧：9ブロック目以降。4,096は出力側の制限で、検索文脈の文字数・トークン数制限ではない。
検索だけを確かめる入口： /retrieve_context は同じ検索・整形を行い、context、チャンク、entity/relationship ID、参照情報を返す。回答用LLM・履歴の読み書きは使わない。ただし埋め込みとリランカーは使う。graph モードは検索自体にLLMが必要なので対象外。

根拠：QA_integration.py:182, 311, 421, 711、rerank_retriever.py:612, 925, 1000、retrieve_only.py:117

04 / top-k and score semantics

「top-kはいくつ？」の正確な答え

アプリの candidate_k=20 と、索引内部で多めに取る件数は別。インストール済みの langchain-neo4j 0.9.0 / neo4j-graphrag 1.22.0 の実装も確認した。

hybrid_score(node) = max(vector_score / max_vector_score,
　　　　　　　　　　　　 fulltext_score / max_fulltext_score)
→ 上位20件 → score ≥ 0.5 → リランク → 上位6件

これは加重平均やRRFではなく、各枝内で正規化した点数の max を使う方式。0.5は「回答が正しい確率50%」を意味しない。ベクトル単独モードの場合は全文枝もこの正規化統合もなく、Neo4jが返すベクトル点数に閾値を掛ける。

点数何と何を比べるか使い道
候補検索 score質問とチャンクのベクトル／全文検索統合top-20と0.5閾値
チャンクのリランク score検索用質問 × チャンク本文の先頭3,000文字上位6件、文書ブロックの順位
エンティティ qsim検索用質問embedding × Entity.embedding文書別40起点の順序、0/1/2ホップ分岐
グラフ行のリランク score検索用質問 × Entity/Relationshipを文字列化した行120行・残り文字予算への採用順
参照リンク score検索用質問 × 参照の一文など（link方式）参照をたどるか。現在のtarget方式とは別
文書を選択して絞った場合は？

vector / graph_vector は文書フィルタを使える。ライブラリはその場合、フィルタ条件に合うノードの厳密なベクトル類似度を計算してtop-kを取る経路へ変わるため、上図の「索引100件要求」をそのまま当てはめない。fulltext / graph_vector_fulltext は文書フィルタ非対応で、文書選択があるとQA側が解除を促して検索しない。

根拠：インストール済み検索ライブラリ、rerank_retriever.py:612、QA_integration.py:737

05 / entity selection and traversal

どのエンティティを起点にするか

現在のグラフ＋ベクトル検索では、最初から全エンティティの中を検索しない。まず本文チャンクを選び、そのチャンクに付いたエンティティから起点を決める。全エンティティのベクトル索引を先に検索するのは別の entity_vector モード。

選択チャンク（直接＋参照）
  └─ PART_OF → 元Documentでグループ分け
       └─ HAS_ENTITY → 起点候補 e
            qsim = vector.similarity.cosine(query_vector, e.embedding)
            numChunks = count(*)  // この選択チャンク群との接続数
            ORDER BY coalesce(qsim, -1) DESC, numChunks DESC
            LIMIT 40             // 文書ごと。全検索合計ではない
                └─ 起点のqsimでホップ数を決めて展開
                     └─ 文書ごとにノード・関係の重複を除去

40の単位は「起点／文書」

例えば3文書からチャンクが採用されれば、起点は最大40×3件の枠を持つ。近傍展開で追加したノードはこの40件に含まれず、展開後のエンティティ総数は40を超え得る。複数文書に同じ起点があれば重なる。

出現数は全文書の頻度ではない

numChunks=count(*) は今選んだチャンクとそのエンティティの接続数。データベース全体での出現頻度ではない。entity_order=count に変えるとこれを優先するが、同数時の順序は指定されていない。

ホップの判定表

起点の類似度 qsim現在の展開注意点
埋め込みなし / null0〜1ホップ起点選択の順位は後ろになるが、選ばれると1ホップ展開
qsim < 0.30ホップ：起点のみエンティティ自体を削除する条件ではない
0.3 ≤ qsim ≤ 0.90〜1ホップ0.3と0.9ちょうどを含む。現在の経路上限0＝無制限
qsim > 0.90〜2ホップ起点ごと最大40経路。two_hop=falseなら1ホップ

数値を動かして分岐を確認

説明用の分岐デモ。実際のグラフ検索や設定変更は行いません。

展開は「経路」を取ってからノードを集める

1ホップの形：
(e)(()-[rels:!HAS_ENTITY&!PART_OF]-()){0,1}(:!Chunk&!Document&!__Community__)

2ホップの形：
(e)(()-[rels:!HAS_ENTITY&!PART_OF]-()){0,2}(:!Chunk&!Document&!__Community__)
RETURN path LIMIT 40

無方向にたどるため、関係の向きが逆でも到達できる。HAS_ENTITY と PART_OF は展開に使わない。終点はChunk・Document・Community以外だが、この終点条件がすべての中間ノードにも掛かっているわけではない。

「40経路」は「関連度の高い40ノード」ではない。

0ホップの起点自身も経路に含む。経路取得に ORDER BY はなく、関連度順・作成順は保証されない。類似度判定をするのは起点で、近傍ノード一つ一つを質問との類似度で落とす処理はない。上限を変えると、あとでグラフ行のリランクに渡る情報量が変わる。

根拠：rerank_retriever.py:228–268、constants.py:368, 465

06 / following document references

「別表による」をどうたどるか

REFERS_TO はエンティティのホップ展開とは別の機能。参照先の本文チャンクを追加し、それもエンティティ選択・展開の起点にする。リンクは取り込み後の link_chunk_references 後処理などで事前に作られている必要がある。

参照先本文と質問の近さで選ぶ

  1. 選択6件から出る、Chunk向けの REFERS_TO を1回たどる。Documentノード向け参照は対象外。
  2. 直接選択済みを除き、DISTINCT … LIMIT 100。この100行の取得には順序指定がない。文書フィルタがあればここでも適用する。
  3. 参照先本文を質問でリランクし、最大2件を追加する。
0.3の参照点数下限はtargetでは使わない。

reference_min_score や reference_depth はlink方式向け。現在のtarget方式では、本文リランクの上位2件を採る。参照リンクがなければ追加しない。

参照先は通常の文書ブロックとしてまとまる。採用した先は返却できるが、target方式の参照記録には「どのquoteからたどったか」が残らない。

質問に関係する「参照の一文」を選んでたどる

  1. 参照リンクを最大2,000行取得（順序指定なし）。参照元・quote・locator・種別でまとめる。
  2. 「見出し＋直前の一文（末尾最大200文字）＋参照の一文」をリランク。直前文が別の参照文なら付けない。
  3. 点数×改正履歴の重みが0.3以上、かつ正のものを上位から最大2参照採用。参照先が重複すれば一つにする。
  4. 参照が複数Chunkを指す場合は「質問＋quote」で再採点して一つにする。Documentだけを指す場合は、文書内の埋め込み上位30候補／文書から本文を再採点し、下限以上の最良1件を選ぶ。

reference_depth=2 なら、1回目の追加チャンクごとに最大1件だけさらに追加。2回目はChunk向けリンクのみ。判定点数は1回目の点数×2回目の点数×履歴重みで、同じ下限を使う。

reference_presentation=inline なら参照先本文を参照元の直後へ移す。移動した本文は単独文書の順位を押し上げず、参照元ブロックに同居する。reference_prompt=true は回答指示に参照の扱いを追加する独立設定。

上限はtargetとlinkで別々に使う

link方式の追加に加えてtarget方式の上位分も追加し、同じチャンクだけ重複除去する。

reference_max = 2 / rerank_top_n = 6
depth=1：直接6 + link最大2 + target最大2 = 最大10
depth=2：上記 + linkの2回目最大2 = 最大12

これはチャンクの選択段階の上限。その後の文書ブロック数・行予算で情報が落ち得るため、全部が最終プロンプトに残る保証ではない。

根拠：rerank_retriever.py:52, 619, 647, 753, 925、score.py:370

07 / what is cut from the final context

文字数と行数で、何を捨てるか

グラフ展開の結果を文章に直すと、本文・エンティティ行・関係行の3つの節になる。現在はエンティティ行と関係行を混ぜてリランクするため、「必ず関係行を優先」とは限らない。

Text Content:
採用されたチャンク本文 …
----
Entities:
Procedure:点検手順 (説明 …)
Equipment:ポンプA
----
Relationships:
Procedure:点検手順 APPLIES_TO Equipment:ポンプA

上の名称・内容は形式を示す架空例です。

現在の行選別アルゴリズム

used = 全文書の本文部分の文字数合計
pool = 全文書の関係行・エンティティ行
pool = 同一文字列を重複除去（最初の文書に所属）
scores = rerank(検索用質問, pool)
kept = 0

for 行 in scores降順:
    if score < 0.0: break          // line_min_score
    if kept >= 120: break          // line_max
    if used + len(行) + 1 > 14000:
        break                     // 短い下位行を探さず全体終了
    行を元の文書へ追加
    used += len(行) + 1
    kept += 1

本文は削らない
各文書にEntities / Relationships見出しを付け直す

本文が16,000文字なら？

14,000文字をすでに超えていても、本文はそのまま残る。追加のグラフ行は0件になる。本文を14,000文字に切る処理ではない。

予算に含まれないもの

再追加する節見出し、出典付きDocumentラッパー、システム指示、質問、会話履歴はこの14,000文字に含まれない。文字数はトークン数でもない。

文字数予算の動作を試す

説明用シミュレーター。架空の200グラフ行を、すでに点数順に並んでいるものとして計算します。実際の検索結果ではありません。

予算は14,000文字。行末の1文字も加算。
残す本文
採用グラフ行
予算内で計上した文字数

最後の「8ブロック」は、この処理の後

format_documents() は文書スコア順の documents[:8] を使う。リランク経路では通常、元文書ごとのブロックなので、同一文書から6チャンクを取っても1ブロックにまとまる。現在の直接6＋target2なら通常は8文書以内であり、最後の8件制限が追加の切り捨てを起こすとは限らない。

上限を増やした場合やboth参照で文書が増える場合には、9文書目以降が丸ごと消える。行予算の計算は先に済んでいるため、最後に消える文書のグラフ行が、途中では文字予算を使っている場合もある。

画面にグラフが見えても、LLMがその関係を読んだとは限らない。

行の選別後も metadata.entities.entityids / relationshipids は展開時の値のまま。根拠を精査するなら、ID一覧だけでなく最終 context の文字列を見る必要がある。

行リランクOFF時と、リランカー故障時は？

CHAT_LINE_RERANK_ENABLED=false なら関係行→エンティティ行の順に、文書間で順番に1行ずつ配る。この経路では line_max / line_min_score は使わない。本文を残す方針は同じ。

チャンクのリランクが通信エラーなどで使えなければ検索点数の順へ戻る。行のリランク失敗は元の行順へ戻る。複数バッチの一部だけが失敗した場合は、そのバッチが0点のままになることもある。通常のリランクは1回200件の束、タイムアウト120秒。

根拠：rerank_retriever.py:289, 339, 377, 962、QA_integration.py:182

08 / retrieval modes

モードが変わると、同じ数値は使わない

mode最初の索引と件数グラフ展開文書選択
vectorChunk vector。現在20候補→6エンティティ展開なし。参照追加は設定に従う可
fulltextChunk vector＋keyword。現在20→6エンティティ展開なし不可
graph_vectorChunk vector。現在20→6選択Chunk→起点40／文書→0〜2ホップ可
graph_vector_fulltextChunk vector＋keyword。現在20→6このページの主経路不可
entity_vectorEntity vector のtop-k=10Chunk上位3、Community上位3、選択Entity間の関係、外部近傍上位10など不可
global_vectorCommunity vector＋keyword のtop-k=10コミュニティ要約を使う。利用には対応データ・索引が必要不可

リランク無効時の旧経路

Chunkモード：
modeの top_k=5 で検索（文書単位の集約・展開はretrieval_query内）
  → 文書行の検索点数に0.5閾値
  → TokenTextSplitterで3,000トークンの断片へ（overlap=0）
  → EmbeddingsFilterで質問との類似度0.10により断片を選別
  → format_documentsで最大8断片（現在の環境値）
  → 回答生成

旧グラフ展開では起点を出現数順の40件にし、0.3／0.9の分岐は同様だが、1ホップ20経路・2ホップ40経路。現在の新経路の「類似度順・1ホップ無制限・行リランク予算」と同じではない。

entity_vector と global_vector は索引ラベルがChunkではないため、CHAT_RERANK_ENABLED=true でもChunk用の20→6経路には入らず、従来の断片分割・埋め込みフィルタを通る。Entityモードの「外部近傍10」は隣接ノード群の上限で、厳密に関係10本という意味ではない。選択Entity同士の関係にはこのクエリ上、件数上限がない。

根拠：constants.py:338, 362, 543, 712, 751、QA_integration.py:311, 401, 421, 583

09 / ingestion and extraction

検索の前に、何が保存されているか

検索を広げても、取り込みで保存されなかった本文・抽出されなかった関係は取り戻せない。検索側の制限とは分けて見る。

読み込みとチャンキング

現在の PDF_CHUNK_STRATEGY=markdown では、ローカルPDFをMarkdown化する経路を先に試す。文字層がない、または変換できない場合は、設定に応じたEDCのOCR変換、その後PyMuPDFへフォールバックする。

項目確認値実際の処理
チャンクサイズ512 tokenリポジトリのフロント用設定値。画面設定・リクエストで変わり得る
重なり / 結合数50 token / 1前後の重なりを指定。抽出前の結合は現在1チャンク。増やすと複数本文を一括抽出
Markdownの長さ計測ruri tokenizer現在はローカルtokenizer.jsonを使用。通常のTokenTextSplitter経路と同じ数え方とは限らない
見出しパンくず最大チャンクサイズの1/4文書名・見出し階層を本文先頭へ追加し、その分本文容量を減らす。表を分割するときは列見出しを付け直す
文書単位の上限200,000通常経路は floor(200000 / 512)=390チャンクで切る。Markdownはbody_tokensの累計で判定する
処理バッチ20チャンク各バッチで埋め込み→抽出→保存→処理数更新。バッチ境界でキャンセル状態を確認

通常経路の390チャンクは「元本文の重複なし200,000トークン」の保証ではない。Markdown経路では上限を超えたチャンクごと、その先を切り捨てる。上限なしの設定・一部ユーザー条件の例外もコードにある。

EDCと汎用LLMの分岐

EDC

/healthを確認し、doctype=autoなら /classify。呼び出し対象の先頭3結合チャンク、最大3,000文字を使う。その後 /extract を同時数制限付きで呼ぶ（構成の既定は2）。

トリプルをNode・Relationshipへ変換。主語・関係・目的語が欠ければトリプル全体を除く。同一トリプルを重複除去し、型情報を優先する。

現在は enrich_schema=true、未知関係の折り畳みと文のような名称の除外も有効。すべてが単純な「統制スキーマのみ」になるとは限らない。画面の許可ノード・許可関係はこのEDC分岐では使わず、EDC側のdoctype管理を使う。

汎用LLM / gemma4など

LLMGraphTransformer に許可ノード・許可関係・追加指示を渡す。構造化出力が使えるモデルではdescriptionも対象にする。

結合チャンクごとに非同期変換し、一部の失敗はスキップする。ローカル互換LLMの出力上限は現在4,096トークン。これはこのローカル経路の値で、EDCサイドカー内部の生成設定とは別。

元のチャンクID一覧を抽出結果に持たせ、保存後に HAS_ENTITY を作る。結合数を増やした場合、抽出結果は結合元の複数チャンクへ紐付く。

Completedでも、全チャンクから全関係を抽出できたとは限らない。

EDC・汎用LLMとも、一部の抽出エラーはスキップして続行し、バッチの処理済み件数は進む。全部失敗したバッチはエラーになる。EDCが返すtruncated/noise/droppedの情報はログに記録される。抽出失敗でも本文・埋め込みが先に保存されていれば本文検索の対象にはなり得る。

実装上の細部：分類・ID・後処理

EDCの分類関数のコメントは「ファイルで1回」だが、呼び出しは処理バッチごとなので、実際には各バッチの先頭サンプルで再分類され得る。

Chunk IDは本文SHA-1。異なる文書でも本文が完全一致すれば同一IDとなり、MERGEで共有され得る。そのため上で説明した「通常1チャンク1文書」「6＋2で最大8文書」は一般的な構成での目安で、複数PART_OF接続があると厳密には変わる。

後処理には索引、Entity埋め込み、類似関係、参照リンク、Community作成などがある。Entity埋め込みがないと検索時のqsimがnullになり、選ばれた起点は1ホップ分岐に入る。現在 GRAPH_SCHEMA_CONSOLIDATION_ENABLED=false。

根拠：create_chunks.py:52, 111, 209、local_file.py:85、main.py:470, 664、llm.py:203, 274 / edc_extraction.py:134, 188, 240

11 / evidence loss map

欲しい根拠が出ないとき、どこを見るか

どの上限を上げればよいかは、情報が落ちた場所で変わる。最後の出力だけから「top-kを増やせば直る」とは決められない。
